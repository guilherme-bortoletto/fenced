# 4. The text gate reads a Python file as its docstrings and its comments

Status: accepted
Date: 2026-09-18

## Context

Attribution and a link back to the run that produced a text are the one thing that arrives in a
public place without anybody writing it. A tool appends the line after the text was written, which
is after the person or the agent that wrote it has read it for the last time.

Until now the pattern that names those forms ran in one place only, over the message of a git
command, inside the hook. The gate aimed at a published body, `--text`, did not look for them at
all. So the body of a pull request passed the gate, went out through a publishing tool, and came
back carrying a line the repository says it never carries. That is what happened to the body of
pull request 12.

Moving the pattern into the text rules raises a question the other rules never had to answer. The
gate has to hold these forms as literals to refuse them. The test has to plant them to prove the
gate refuses them. If the rule reads every line of every tracked file, then the file that refuses
the form and the test that plants it both break the rule, and the only ways out are worse than the
hole. Assembling the pattern from pieces so it does not read as itself hides the rule from the
reader. Adding an exception for two paths leaves an exception anyone can move into.

There is already an answer in this file for the other text rules. A Python file is code, and the
text of it is the docstrings. Punctuation rules run over the docstrings and not over the source.

## Decision

The text rules refuse attribution and a session link, in a file given to `--text` and in every
tracked text file the default run reads.

What counts as the text of a file depends on what the file is. A Markdown file, or anything else
handed to the gate, is read line by line exactly as it stands, with nothing taken out, because the
link is half of what is being looked for and Markdown prose has the links taken out of it. A Python
file is read as its docstrings and its comments, which is every line of it a reader reads as text. A
string literal in a Python file is data the program holds, and it stays data.

That is what lets `scripts/gates.py` carry the pattern and `tests/test_gates.py` plant each form,
both of them as literals, in plain sight, with no exception list and no path spelled out anywhere.
A test asserts it, by running the gate over those two files and expecting nothing.

The pattern also grew a form it was missing. It read `generated with` and not `generated by`, and
`generated by` is the wording of the footer that reached pull request 12.

The check over the message of a git command stays where it was, as `message_problems`, because a
message is text that no file ever holds.

## Consequences

A body is refused before it is published, and the same command refuses it after. Reading a
published body back and running the gate over it is now worth doing, because the gate has something
to say about it. `AGENTS.md` says to do that.

A comment in a Python file is now read by one rule and not by the others. That asymmetry is
deliberate and it is written down here, because a reader who finds a hyphen in a comment and no
complaint from the gate will otherwise think the gate is broken.

A Python file whose comments cannot be tokenized is refused with the same line as a file that will
not parse. A gate that cannot read a file does not pass it.

The hole that is left is a string literal in a Python file. Anything can be written there and no
text rule will see it. That is the price of a gate that can name what it refuses, and the fence
that matters for a published body does not depend on it, because a body is never a Python file.
